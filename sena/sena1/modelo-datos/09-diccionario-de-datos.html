1. Descripción general del modelo

La base de datos db_nodejs está compuesta por seis tablas de dominio y dos tablas de control que la herramienta de migraciones administra por su cuenta. Todas las tablas de dominio comparten la misma convención estructural.

1.1 Convenciones aplicadas a todas las tablas

Tabla 1. Convenciones estructurales comunes.
ConvenciónDescripción y motivo
Llave primaria UUIDTodas las tablas usan id UUID como llave primaria. Un identificador secuencial revelaría el volumen de registros y permitiría recorrer recursos probando números consecutivos.
Campo is_activeBooleano con valor por omisión true. La eliminación es siempre lógica: el registro se marca inactivo pero permanece, de modo que el historial que lo referencia se conserva íntegro.
Marcas de tiempocreatedAt y updatedAt con zona horaria, administradas automáticamente por el ORM. Aportan trazabilidad sin código adicional.
Nombres en pluralLas tablas se nombran en plural y en minúsculas, salvo inventario, que es un sustantivo incontable.
Sufijo _idToda llave foránea lleva el nombre de la tabla referenciada en singular más el sufijo _id.
Restricciones en el motorLas reglas críticas (unicidad, cantidad no negativa, cantidad mayor que cero) se declaran en la base de datos y no solo en la aplicación, de modo que se cumplen aunque el dato entre por otra vía.

Restricciones de inventario

Nombre de la restricciónTipoDefinición y propósito
inventario_pkeyPRIMARY KEY(id)
inventario_almacen_id_fkeyFOREIGN KEY(almacen_id) → almacenes(id). Impide inventario de un almacén inexistente.
inventario_medicamento_id_fkeyFOREIGN KEY(medicamento_id) → medicamentos(id). Impide inventario de un medicamento inexistente.
inventario_almacen_medicamento_unicoUNIQUE(almacen_id, medicamento_id). Un almacén no puede tener dos filas del mismo medicamento, lo que haría ambigua la cantidad disponible.
inventario_cantidad_no_negativaCHECK(cantidad >= 0). Última línea de defensa: aunque un error de la aplicación intentara descontar de más, el motor rechaza la operación.

3. Relaciones entre tablas

Tabla 10. Relaciones del modelo, su cardinalidad y su justificación.
RelaciónCardinalidadJustificación
almacenes → inventario1 : NUn almacén guarda muchos medicamentos distintos; cada fila de inventario pertenece a un solo almacén.
medicamentos → inventario1 : NUn medicamento puede estar en varios almacenes; cada fila de inventario corresponde a un solo medicamento.
clinicas → solicitudes1 : NUna clínica radica muchas solicitudes a lo largo del tiempo; cada solicitud proviene de una sola clínica.
medicamentos → solicitudes1 : NCada solicitud pide un solo medicamento. Para pedir varios se radican varias solicitudes, de modo que cada una se aprueba o rechaza por separado.
almacenes → solicitudes1 : NCada solicitud se asigna a un solo almacén de despacho, que es del que se descontará el inventario.
users → solicitudes1 : NUn usuario registra muchas solicitudes; cada solicitud tiene un único autor, lo que permite auditar quién la radicó.
almacenes ↔ medicamentosN : MRelación de muchos a muchos resuelta mediante la tabla intermedia inventario, que añade el atributo propio cantidad.
Sobre la relación de muchos a muchos Una tabla intermedia con atributos propios no es una simple tabla de unión: inventario existe porque la cantidad disponible no pertenece ni al almacén ni al medicamento por separado, sino a la combinación de ambos. Guardar la cantidad en medicamentos obligaría a duplicar la fila del medicamento por cada almacén.

4. Normalización del modelo

El modelo cumple la tercera forma normal. Se documenta la verificación para cada nivel.

Tabla 11. Verificación de las formas normales.
Forma normalCondiciónVerificación en este modelo
1FNTodos los atributos son atómicos; no hay grupos repetidos.Ninguna columna almacena listas ni valores compuestos. Los datos del responsable de la clínica se guardan en tres columnas independientes en lugar de un solo campo de texto.
2FNCumple 1FN y todo atributo no clave depende de la llave primaria completa.Todas las llaves primarias son un único campo id, por lo que no existen dependencias parciales. En inventario, aunque la pareja almacén-medicamento sea única, cantidad depende de esa combinación completa, nunca de uno solo de los dos.
3FNCumple 2FN y no existen dependencias transitivas entre atributos no clave.Los datos del medicamento no se repiten en solicitudes: esta guarda únicamente medicamento_id. Lo mismo aplica a clínica, almacén y usuario. El nombre del medicamento se obtiene por relación, no por duplicación.
Decisión consciente: cantidad_solicitada no se recalcula La columna cantidad_solicitada de una solicitud conserva el valor con el que fue radicada aunque después cambie el inventario. Esto no es redundancia: es un dato histórico propio de la solicitud, necesario para poder reintegrar exactamente la misma cantidad si más adelante se cancela.

5. Datos de prueba cargados

Los seeders del proyecto cargan un conjunto de datos coherente que cubre todos los estados del sistema. Se ejecutan en orden numérico porque cada uno depende del anterior.

Tabla 12. Volumen de datos de prueba por tabla.
TablaRegistrosContenido
users4Dos administradores y dos gestores, con las contraseñas ya cifradas con bcrypt.
clinicas3Tres clínicas con NIT distinto y sus responsables.
almacenes2Dos almacenes de despacho.
medicamentos6Seis productos del catálogo con presentación y laboratorio.
inventario9Nueve combinaciones de almacén y medicamento con cantidades distintas.
solicitudes6Seis solicitudes, una por cada estado posible, para poder probar todo el ciclo.
Cómo resuelven los seeders los identificadores Como las llaves primarias son UUID generados al azar en cada ejecución, los seeders no pueden escribirlos a mano. Cada seeder consulta las tablas anteriores y localiza los registros por su nombre, o por el correo en el caso de los usuarios, y con ese resultado arma las llaves foráneas. Por eso el orden de ejecución es obligatorio.

5.1 Reconstrucción completa de la base de datos

# 1. Limpiar el registro de seeders ejecutados
npm run seed:reset

# 2. Borrar todas las tablas
npm run migrate:reset

# 3. Volver a crear la estructura
npm run migrate

# 4. Cargar de nuevo los datos de prueba
npm run seed
El orden importa migrate:reset borra las tablas del dominio, pero el registro que la herramienta lleva de los seeders sobrevive en la tabla SequelizeData. Si no se ejecuta seed:reset primero, el comando seed asume que los seeders ya corrieron, no carga nada y las tablas quedan vacías.

5.2 Restauración desde el respaldo

El repositorio incluye backup.sql, un respaldo completo con estructura y datos ya cargados.

createdb -h localhost -U admin db_nodejs
psql -h localhost -U admin -d db_nodejs -f backup.sql
