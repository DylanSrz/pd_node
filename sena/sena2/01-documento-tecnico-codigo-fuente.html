1. Organización del proyecto

1.1 Estructura de directorios

El proyecto agrupa los archivos por responsabilidad técnica y no por entidad de negocio. Es decir, existe una carpeta services con los servicios de todas las entidades, y no una carpeta clinicas que contenga su modelo, su servicio y su controlador. Esta decisión hace visible la arquitectura por capas desde el propio árbol de archivos.

3. Explicación de las capas

3.1 Regla de dependencia

El código respeta una regla única y verificable: cada capa solo importa de la capa inmediatamente inferior. Esta restricción se puede comprobar leyendo las importaciones de cualquier archivo.

RUTA importa -> middlewares, controladores, esquemas MIDDLEWARE importa -> servicios, modelos, utilidades CONTROLADOR importa -> servicios SERVICIO importa -> modelos, utilidades, tipos MODELO importa -> configuracion de la base de datos, tipos Lo que NUNCA ocurre: un servicio importa Request o Response de Express un controlador importa un modelo directamente un modelo importa a otro modelo
Por qué un servicio no conoce Express Los servicios reciben datos ya validados y devuelven datos o lanzan un error de negocio. Nunca escriben una respuesta HTTP. Gracias a eso, la misma función crearSolicitud podría invocarse desde una tarea programada, desde una interfaz de línea de comandos o desde una prueba automatizada, sin arrastrar consigo el protocolo HTTP.

4. Capa de configuración

4.1 Conexión con la base de datos

El archivo src/config/db.ts crea una única instancia de Sequelize que se comparte en todo el proyecto. Ningún otro archivo crea conexiones adicionales.

import { Sequelize } from "sequelize";
import "dotenv/config";

const {
    DATABASE_HOST, DATABASE_PORT, DATABASE_USER,
    DATABASE_PASSWORD, DATABASE_NAME
} = process.env;

const db = new Sequelize(
    DATABASE_NAME || "",
    DATABASE_USER || "",
    DATABASE_PASSWORD || "",
    {
        host: DATABASE_HOST || "localhost",

        // Dentro del contenedor, docker-compose fija DATABASE_PORT
        // en 5432. Fuera de Docker se usa el valor del .env.
        port: Number(DATABASE_PORT) || 5432,

        dialect: "postgres",
        logging: console.log,
    }
);

export default db;

Decisión técnica. Cada variable tiene un valor de respaldo con el operador ||. Esto evita que la aplicación falle con un error opaco de tipo si una variable no está definida, y hace explícito el comportamiento esperado en ausencia de configuración.

4.2 Configuración de las migraciones

El archivo src/config/migrator.ts configura Umzug. Contiene una decisión que merece atención: el patrón de búsqueda de archivos cambia según si el proyecto se ejecuta desde el código fuente o desde la versión compilada.

import { SequelizeStorage, Umzug } from "umzug";
import db from "./db.js";

// En desarrollo este archivo se ejecuta como .ts con tsx;
// compilado, como .js dentro de dist.
// El glob tiene que apuntar al mismo formato en cada caso.
const isCompiled = import.meta.url.endsWith('.js');

export const migrator = new Umzug({
    migrations: {
        glob: isCompiled
            ? 'dist/migrations/*.js'
            : 'src/migrations/*.ts'
    },
    context: db.getQueryInterface(),
    storage: new SequelizeStorage({
        sequelize: db,
        tableName: 'migrations',
        timestamps: true
    }),
    logger: console
});
Por qué esta comprobación es necesaria Sin ella, el mismo archivo buscaría archivos .ts dentro de un contenedor de producción que solo contiene .js, y las migraciones sencillamente no encontrarían nada que ejecutar, fallando en silencio. La propiedad import.meta.url permite al módulo saber bajo qué extensión se está ejecutando.

El objeto context es la interfaz de consultas de Sequelize, que es exactamente lo que cada migración recibe como parámetro para crear o eliminar tablas.

5. Capa de modelos

5.1 Anatomía de un modelo

Cada modelo declara primero los campos como propiedades tipadas de la clase y después los define para Sequelize. La doble declaración permite que TypeScript conozca el tipo de solicitud.estado sin necesidad de conversiones.

class Solicitud extends Model {
    // Identificador unico de la solicitud.
    declare id: string;

    // Estado actual dentro del ciclo de vida.
    declare estado: EstadoSolicitud;

    // Nota opcional al cambiar el estado.
    declare observaciones: string | null;
    // ... resto de campos
}

Solicitud.init(
    {
        id: {
            type: DataTypes.UUID,
            defaultValue: DataTypes.UUIDV4,
            primaryKey: true,
        },
        cantidad_solicitada: {
            type: DataTypes.INTEGER,
            allowNull: false,
        },
        estado: {
            type: DataTypes.ENUM(...ESTADOS_SOLICITUD),
            allowNull: false,

            // Toda solicitud nace en estado pendiente.
            defaultValue: "pendiente",
        },
        // ...
    },
    { sequelize: db, tableName: "solicitudes", timestamps: true }
);

La palabra clave declare le indica a TypeScript el tipo de la propiedad sin generar código que la inicialice. Es indispensable con Sequelize, porque la biblioteca define esas propiedades mediante descriptores en tiempo de ejecución; una declaración normal las sobrescribiría con undefined.

El operador de propagación en DataTypes.ENUM(...ESTADOS_SOLICITUD) expande la lista constante definida en types/enums.ts. Los estados quedan escritos una sola vez y se reutilizan en el modelo, en la migración, en el esquema de validación y en la máquina de estados.

5.2 Cifrado de la contraseña mediante un gancho

El modelo User incorpora un gancho que se dispara automáticamente antes de crear cualquier usuario.

// Antes de guardar un usuario nuevo: se pasan los textos a
// minusculas y se cifra la contrasena.
User.beforeCreate(async (user: User) => {
    user.first_name = user.first_name.toLowerCase();
    user.last_name  = user.last_name.toLowerCase();
    user.email      = user.email.toLowerCase();

    // bcrypt convierte la contrasena en un hash irreversible.
    user.password_hash = await bcrypt.hash(user.password_hash, 10);
});
Ventaja de resolverlo en el modelo y no en el servicio La contraseña queda cifrada sin importar por dónde se cree el usuario. Si más adelante se agrega un comando de administración o una carga masiva, no hay riesgo de olvidar el cifrado: es imposible guardar un usuario sin pasar por este gancho.

El número 10 es el factor de costo: indica cuántas rondas de derivación aplica bcrypt. A mayor valor, más lento resulta tanto cifrar como intentar romper el hash por fuerza bruta.

5.3 Asociaciones centralizadas

Todas las relaciones entre modelos se declaran en un único archivo, models/index.ts.

// ------------------------------------------------------
// INVENTARIO
// Almacen 1 ---- N Inventario N ---- 1 Medicamento
// ------------------------------------------------------

Inventario.belongsTo(Almacen,  { foreignKey: "almacen_id",     as: "almacen" });
Almacen.hasMany(Inventario,   { foreignKey: "almacen_id",     as: "inventario" });

Inventario.belongsTo(Medicamento, { foreignKey: "medicamento_id", as: "medicamento" });
Medicamento.hasMany(Inventario,  { foreignKey: "medicamento_id", as: "inventario" });

// Se exportan todos juntos para importarlos comodamente
// desde los services.
export { User, Clinica, Almacen, Medicamento, Inventario, Solicitud };
Problema que resuelve la centralización Si solicitud.model.ts importara clinica.model.ts para declarar su relación, y clinica.model.ts importara solicitud.model.ts para declarar la inversa, se produciría una importación circular: al cargarse el primero, el segundo aún no existiría y una de las dos referencias sería undefined. Declarar todas las asociaciones en un tercer archivo, importado desde app.ts antes de atender peticiones, elimina por completo esa posibilidad.

Los alias definidos en as son los que después permiten a los servicios pedir las relaciones incluidas y los que dan nombre a las propiedades anidadas de la respuesta JSON.

6. Capa de validación

6.1 Esquema y tipo derivado

Cada esquema de dto/ cumple dos funciones simultáneas: valida en tiempo de ejecución y genera el tipo de TypeScript correspondiente.

export const crearSolicitudSchema = z.object({
    clinica_id: z.uuid("El clinica_id es obligatorio y debe tener formato UUID."),

    medicamento_id: z.uuid("El medicamento_id es obligatorio..."),

    almacen_id: z.uuid("El almacen_id es obligatorio..."),

    cantidad_solicitada: z
        .number({ error: "La cantidad solicitada es obligatoria..." })
        .int("La cantidad solicitada debe ser un numero entero.")
        .positive("La cantidad solicitada debe ser mayor que cero."),

    observaciones: z.string()
        .max(500, "Las observaciones no pueden superar los 500 caracteres.")
        .optional(),
});

// El tipo se deduce del esquema: los campos se escriben una sola vez.
export type CrearSolicitudInput = z.infer<typeof crearSolicitudSchema>;
Ventaja de derivar el tipo del esquema Si mañana se agrega un campo obligatorio al esquema, el tipo cambia automáticamente y el compilador señala todos los lugares que dejan de ser válidos. Con una interfaz escrita a mano en paralelo, esa desincronización pasaría inadvertida hasta producir un fallo en ejecución.

Obsérvese qué campos no aparecen en el esquema. No se pide usuario_id, porque se toma del token, y no se pide estado, porque toda solicitud nace pendiente. Lo que el esquema omite es tan significativo como lo que incluye: define la superficie de entrada del sistema.

6.2 Validación de actualizaciones parciales

El esquema de actualización usa un refinamiento para rechazar cuerpos vacíos.

export const actualizarSolicitudSchema = z
    .object({
        cantidad_solicitada: z.number().int().positive().optional(),
        observaciones: z.string().max(500).optional(),
    })
    .refine((datos) => Object.keys(datos).length > 0, {
        message: "Debe enviar al menos un campo para actualizar.",
    });

Sin ese refinamiento, una petición con el cuerpo {} pasaría la validación, llegaría al servicio y ejecutaría una actualización que no cambia nada, devolviendo un 200 engañoso.

7. Capa de middlewares

7.1 Autenticación

export function verifyToken(req: Request, res: Response, next: NextFunction): void {
    const cabecera = req.headers.authorization;

    // Sin cabecera Authorization no hay nada que validar.
    if (!cabecera || !cabecera.startsWith("Bearer ")) {
        res.status(401).json({ message: "Token no proporcionado." });
        return;
    }

    // La cabecera viene como "Bearer abc.def.ghi".
    const token = cabecera.split(" ")[1];
    // ...

    try {
        // jwt.verify revisa la firma y que el token no este vencido.
        const payload = jwt.verify(token, secreto) as PayloadToken;

        // Se guarda el usuario en la peticion para reutilizarlo despues.
        req.user = payload;
        next();
    } catch {
        res.status(401).json({ message: "Token invalido o expirado." });
    }
}

La asignación req.user = payload solo compila porque el archivo types/express.d.ts amplia la interfaz Request de Express para incluir esa propiedad. Es la forma correcta de extender un tipo de una biblioteca externa sin recurrir a conversiones forzadas.

7.2 Autorización por rol

checkRole es una función que devuelve un middleware. Ese patrón permite configurarla en la propia declaración de la ruta.

export function checkRole(...rolesPermitidos: RolUsuario[]) {
    return (req: Request, res: Response, next: NextFunction): void => {
        const usuario = req.user;

        // Si no hay usuario es porque no paso por verifyToken.
        if (!usuario) {
            res.status(401).json({ message: "Usuario no autenticado." });
            return;
        }

        if (!rolesPermitidos.includes(usuario.role)) {
            res.status(403).json({
                message: "No tiene permisos para realizar esta accion."
            });
            return;
        }

        next();
    };
}

// Uso en una ruta:
router.post("/", checkRole("administrador"), postClinica);

El parámetro tipado como RolUsuario[] impide escribir un rol inexistente: checkRole("supervisor") no compila.

7.3 Validación de reglas de negocio previas

El middleware de inventario ilustra por qué conviene separar estas comprobaciones del servicio.

export async function verificarInventarioDisponible(
    req: Request, res: Response, next: NextFunction
): Promise<void> {
    try {
        const { almacen_id, medicamento_id, cantidad_solicitada } = req.body;

        const registroInventario =
            await buscarInventario(almacen_id, medicamento_id);

        // El almacen nunca ha manejado ese medicamento.
        if (!registroInventario) {
            res.status(400).json({
                message: "El almacen seleccionado no maneja ese medicamento."
            });
            return;
        }

        // Lo maneja, pero no tiene suficientes unidades.
        if (registroInventario.cantidad < cantidad_solicitada) {
            res.status(400).json({
                message: "El almacen no tiene inventario suficiente...",
                cantidad_solicitada: cantidad_solicitada,
                cantidad_disponible: registroInventario.cantidad,
            });
            return;
        }

        next();
    } catch (error) {
        next(error);
    }
}

La respuesta de error no se limita a un mensaje: incluye la cantidad solicitada y la disponible, de modo que quien consume la API puede mostrar un aviso útil sin realizar otra consulta.

7.4 Manejador central de errores

Express reconoce un manejador de errores porque recibe cuatro parámetros y el primero es el error. Va registrado al final de app.ts, después de todas las rutas.

export function errorHandler(
    error: unknown, _req: Request, res: Response, _next: NextFunction
): void {
    // Caso 1: error de negocio que lanzamos nosotros,
    // ya trae su propio codigo HTTP.
    if (error instanceof HttpError) {
        res.status(error.statusCode).json({ message: error.message });
        return;
    }

    // Caso 2: valor repetido en una columna unica.
    if (error instanceof UniqueConstraintError) {
        res.status(409).json({
            message: "Ya existe un registro con esos datos.",
            errors: error.errors.map((d) => d.message),
        });
        return;
    }

    // Caso 3: fallo una validacion del modelo.
    if (error instanceof ValidationError) { /* 400 */ }

    // Caso 4: error inesperado. Se registra en el servidor
    // pero al cliente solo se le devuelve un mensaje generico.
    console.error("Error inesperado:", error);
    res.status(500).json({ message: "Error interno del servidor." });
}
Valor de este patrón El error se declara como unknown y no como any, lo que obliga a comprobar su tipo antes de acceder a sus propiedades. Los cuatro casos están ordenados de lo más específico a lo más general, y el último garantiza que ningún error inesperado filtre su traza al cliente. Sin este manejador, cada uno de los treinta controladores tendría que repetir esta lógica.

8. Capa de servicios

Es la capa que concentra el valor del sistema. Se documentan los tres fragmentos más relevantes.

8.1 La máquina de estados

Las transiciones válidas se declaran como un dato, no como una cadena de condicionales.

/**
 * Mapa con los cambios de estado permitidos.
 * Los estados finales tienen la lista vacia: de ahi no se sale.
 *
 *   pendiente --> aprobada --> entregada   (final)
 *       |             \------> cancelada   (final)
 *       |------> rechazada                 (final)
 *       \------> cancelada                 (final)
 */
export const TRANSICIONES_PERMITIDAS:
    Record<EstadoSolicitud, EstadoSolicitud[]> = {
        pendiente: ["aprobada", "rechazada", "cancelada"],
        aprobada:  ["entregada", "cancelada"],
        rechazada: [],
        entregada: [],
        cancelada: [],
    };

export function esTransicionValida(
    estadoActual: EstadoSolicitud,
    estadoNuevo: EstadoSolicitud
): boolean {
    const estadosPosibles = TRANSICIONES_PERMITIDAS[estadoActual];
    return estadosPosibles.includes(estadoNuevo);
}
Ventajas de modelar las reglas como datos
  • El tipo Record<EstadoSolicitud, ...> obliga a declarar los cinco estados. Si mañana se agrega un estado nuevo al tipo enumerado, el proyecto no compila hasta que se defina a dónde puede transitar.
  • Toda la regla es legible de un vistazo, sin recorrer una cadena de condicionales.
  • La misma estructura alimenta el mensaje de error que se le devuelve al cliente.

8.2 Cambio de estado con transacción y bloqueo de fila

Es el fragmento técnicamente más exigente del proyecto. Se reproduce con sus comentarios originales.

export async function cambiarEstadoSolicitud(
    id: string, datos: CambiarEstadoInput
): Promise<Solicitud> {
    const transaccion = await db.transaction();

    try {
        const solicitud = await Solicitud.findOne({
            where: { id, is_active: true },
            transaction: transaccion,
        });

        if (!solicitud) {
            throw new HttpError(404, "La solicitud no existe o fue eliminada.");
        }

        const estadoAnterior = solicitud.estado;

        // Caso 1: se aprueba, hay que descontar el inventario.
        if (datos.estado === "aprobada") {
            const registroInventario = await Inventario.findOne({
                where: {
                    almacen_id: solicitud.almacen_id,
                    medicamento_id: solicitud.medicamento_id,
                    is_active: true,
                },
                transaction: transaccion,

                // Bloquea la fila hasta que termine la transaccion, para
                // que dos aprobaciones al mismo tiempo no descuenten el
                // mismo stock.
                lock: Transaction.LOCK.UPDATE,
            });

            if (!registroInventario) {
                throw new HttpError(400,
                    "El almacen ya no maneja ese medicamento...");
            }

            // Se vuelve a revisar la cantidad: entre que se creo la
            // solicitud y ahora, otra aprobacion pudo haber consumido
            // el inventario.
            if (registroInventario.cantidad < solicitud.cantidad_solicitada) {
                throw new HttpError(400,
                    `Inventario insuficiente para aprobar. ` +
                    `Disponible: ${registroInventario.cantidad}, ` +
                    `solicitado: ${solicitud.cantidad_solicitada}.`);
            }

            await registroInventario.update(
                { cantidad: registroInventario.cantidad
                           - solicitud.cantidad_solicitada },
                { transaction: transaccion }
            );
        }

        // Caso 2: se cancela una solicitud que ya estaba aprobada,
        // hay que devolver las unidades al almacen.
        if (datos.estado === "cancelada" && estadoAnterior === "aprobada") {
            // ... mismo bloqueo, suma en lugar de resta
        }

        // Ya ajustado el inventario, se guarda el estado nuevo.
        await solicitud.update(
            { estado: datos.estado,
              observaciones: datos.observaciones ?? solicitud.observaciones },
            { transaction: transaccion }
        );

        // commit confirma todos los cambios de la transaccion.
        await transaccion.commit();
        return obtenerSolicitudPorId(id);

    } catch (error) {
        // rollback deshace todo lo que se alcanzo a hacer.
        await transaccion.rollback();
        throw error;
    }
}

Las tres decisiones que sostienen este fragmento

DecisiónProblema que evita
TransacciónSin ella, si el descuento del inventario tuviera éxito pero la actualización del estado fallara, quedaría inventario descontado por una solicitud que sigue pendiente. Con la transacción se aplican ambos cambios o ninguno.
Bloqueo de filaSin LOCK.UPDATE, dos aprobaciones simultáneas del mismo medicamento leerían la misma cantidad, ambas la considerarían suficiente y ambas descontarían sobre el mismo valor. El bloqueo obliga a la segunda a esperar y a leer el valor ya actualizado.
RevalidaciónEntre la creación de la solicitud y su aprobación pueden pasar horas. La comprobación que hizo el middleware al crearla ya no es válida en el momento de aprobar, por eso se repite dentro de la transacción.

8.3 Consultas con relaciones incluidas

La lista de relaciones se declara una sola vez como constante y se reutiliza en todas las consultas del servicio.

// Al consultar solicitudes siempre se traen los datos de las tablas
// relacionadas, para no devolver una lista de UUIDs sin significado.
const incluirRelaciones = [
    { model: Clinica,     as: "clinica",
      attributes: ["id", "nombre", "nit", "responsable_nombre"] },
    { model: Medicamento, as: "medicamento",
      attributes: ["id", "nombre", "presentacion"] },
    { model: Almacen,     as: "almacen",
      attributes: ["id", "nombre"] },
    { model: User,        as: "usuario",
      attributes: ["id", "first_name", "last_name", "email"] },
];

El campo attributes es una decisión de seguridad tanto como de eficiencia: al enumerar explícitamente las columnas del usuario, es imposible que el hash de la contraseña aparezca en una respuesta, incluso por descuido.

8.4 Diferencia entre solicitudes activas e historial

/**
 * Devuelve las solicitudes activas, es decir, las que todavia
 * estan en curso: pendientes o aprobadas.
 */
export async function listarSolicitudesActivas(): Promise<Solicitud[]> {
    return Solicitud.findAll({
        where: { is_active: true, estado: ["pendiente", "aprobada"] },
        include: incluirRelaciones,
        order: [["createdAt", "DESC"]],
    });
}

/**
 * Devuelve el historial completo de solicitudes.
 * Aqui no se filtra por estado ni por is_active a proposito:
 * el historial debe mostrar todo lo que ha pasado.
 */
export async function listarHistorialSolicitudes(): Promise<Solicitud[]> {
    return Solicitud.findAll({
        include: incluirRelaciones,
        order: [["createdAt", "DESC"]],
    });
}

La ausencia de filtros en la segunda función es deliberada y está documentada en el propio código, para que nadie la interprete como un olvido y la "corrija".

9. Capa de controladores y rutas

9.1 Un controlador tipo

Todos los controladores siguen la misma estructura de cinco pasos.

/**
 * POST /api/solicitudes
 * Registra una solicitud. El usuario se toma del token.
 */
export async function postSolicitud(
    req: Request, res: Response, next: NextFunction
): Promise<void> {
    try {
        // 1. Leer lo que ya validaron los middlewares.
        const usuarioId = req.user!.id;

        // 2. Delegar toda la logica al servicio.
        const solicitud = await crearSolicitud(req.body, usuarioId);

        // 3. Elegir el codigo HTTP y responder.
        res.status(201).json({
            message: "Solicitud registrada correctamente.",
            solicitud,
        });
    } catch (error) {
        // 4. Cualquier error va al manejador central.
        next(error);
    }
}

El controlador no contiene ni una sola regla de negocio: no sabe qué es un estado válido ni cómo se descuenta el inventario. Solo traduce entre el protocolo HTTP y la capa de servicios. Esa disciplina es lo que mantiene los controladores en menos de veinte líneas cada uno.

9.2 Encadenamiento de middlewares en una ruta

La declaración de una ruta es, en la práctica, la documentación ejecutable de sus reglas.

// Todas las rutas de solicitudes exigen token.
router.use(verifyToken);

router.get("/", getSolicitudes);

// Va declarada ANTES que /:id. Si estuviera despues, Express
// interpretaria la palabra "historial" como si fuera un id.
router.get("/historial", getHistorialSolicitudes);

router.get("/:id", validateParams(idSchema), getSolicitudPorId);

// Antes de crearla se revisa, en este orden:
//   1. que los datos tengan el formato correcto y cantidad > 0,
//   2. que la clinica, el medicamento y el almacen existan,
//   3. que el almacen tenga inventario suficiente.
router.post(
    "/",
    checkRole("gestor", "administrador"),
    validateRequest(crearSolicitudSchema),
    verificarEntidadesRelacionadas,
    verificarInventarioDisponible,
    postSolicitud
);
Detalle de implementación fácil de pasar por alto El orden de /historial y /:id no es indiferente. Express evalúa las rutas en el orden en que fueron declaradas. Si /:id estuviera primero, una petición a /api/solicitudes/historial haría coincidir el parámetro con el texto historial, la validación de UUID fallaría y el endpoint de historial resultaría inalcanzable. Por eso el código lleva un comentario que advierte a quien lo modifique en el futuro.

9.3 Documentación integrada

La documentación de la API no vive en un archivo aparte: se escribe como comentarios junto a la ruta que describe, y swagger-jsdoc los extrae para construir la especificación OpenAPI que se publica en /api-docs. La consecuencia práctica es que modificar una ruta y olvidar actualizar su documentación exige ignorar un comentario que está a tres líneas de distancia.

10. Migraciones y seeders

10.1 Estructura de una migración

Cada migración exporta dos funciones: up aplica el cambio y down lo revierte.

export async function up({ context }: { context: QueryInterface }) {
    await context.createTable("inventario", {
        id: { type: DataTypes.UUID, defaultValue: DataTypes.UUIDV4,
              primaryKey: true },
        almacen_id: {
            type: DataTypes.UUID, allowNull: false,
            // Llave foranea: inventario.almacen_id -> almacenes.id
            references: { model: "almacenes", key: "id" },
        },
        // ...
    });

    // Evita que se registre dos veces el mismo medicamento
    // en el mismo almacen.
    await context.addConstraint("inventario", {
        fields: ["almacen_id", "medicamento_id"],
        type: "unique",
        name: "inventario_almacen_medicamento_unico",
    });

    // Regla en la propia base de datos para que la cantidad
    // nunca pueda quedar en negativo.
    await context.sequelize.query(`
        ALTER TABLE inventario
        ADD CONSTRAINT inventario_cantidad_no_negativa
        CHECK (cantidad >= 0);
    `);
}

export async function down({ context }: { context: QueryInterface }) {
    await context.dropTable("inventario");
}

La restricción de verificación se declara con SQL directo porque la interfaz de consultas de Sequelize no ofrece un método específico para ese tipo de restricción. Es un ejemplo de dónde conviene bajar del ORM al SQL: la regla es crítica y debe vivir en el motor.

En la migración de users, la función down incluye un detalle propio de PostgreSQL:

export async function down({ context }: { context: QueryInterface }) {
    await context.dropTable("users");

    // PostgreSQL guarda los ENUM como un tipo aparte,
    // por eso hay que eliminarlo a mano.
    await context.sequelize.query('DROP TYPE IF EXISTS "enum_users_role";');
}

Sin esa línea, revertir y volver a aplicar la migración fallaría: el tipo ya existiría.

10.2 Cómo los seeders resuelven los UUID

Los identificadores se generan al azar en cada ejecución, de modo que un seeder no puede escribir a mano la llave foránea que necesita. La solución es consultar la tabla anterior y localizar el registro por un campo estable.

// El inventario necesita los ids reales del almacen y del
// medicamento, que se generaron al azar en los seeders anteriores.
const [almacenes] = await context.sequelize.query(
    `SELECT id, nombre FROM almacenes`
);

const central = almacenes.find((a) => a.nombre === "Almacen Central");

Esta dependencia es la que obliga a que los archivos se ejecuten en orden numérico: 050-inventario necesita que 030-almacenes y 040-medicamentos ya hayan corrido.

Comportamiento no evidente al reiniciar la base de datos El comando migrate:reset borra las tablas del dominio, pero el registro que Umzug lleva de los seeders sobrevive en la tabla SequelizeData. Si no se ejecuta seed:reset primero, el comando seed asume que los seeders ya corrieron, no carga nada y las tablas quedan vacías sin mostrar ningún error. El orden correcto es: seed:reset, migrate:reset, migrate, seed.
